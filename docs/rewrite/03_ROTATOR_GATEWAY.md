# RotatorGateway Integration

## Purpose

`RotatorGateway` is the only ImaginAI service allowed to call `rotator_library`.

```text
GenerationService
  -> RotatorGateway
    -> rotator_library.RotatingClient
```

The gateway keeps the boundary clean. ImaginAI owns product routing and story logic. `rotator_library` owns LLM communication.

## Boundary

ImaginAI owns:

- users
- permissions
- provider connections
- encrypted credentials
- model configs
- global/user visibility
- model picker ordering
- scenario/adventure prompts
- context selection
- card activation
- memory/summary logic
- prompt assembly
- generation intent

`rotator_library` owns:

- provider communication
- streaming and non-streaming completions
- retries/failover
- credential rotation/load balancing
- scoped credential behavior
- quota/cooldown mechanics
- model discovery communication
- provider error classification
- low-level usage metadata

The old/current proxy app is reference material only. ImaginAI should integrate with the library, not depend on the proxy's HTTP server architecture.

## Current Library Capability

The upstream `dev` branch has classifier-scoped routing support. It can handle enough for ImaginAI alpha:

- scoped/classifier credential pools
- runtime scope/provider/credential registration
- per-classifier model discovery and cache
- private mode that avoids raw secret persistence
- scoped `acompletion`, `aembedding`, `get_available_models`
- backward compatibility with global `api_keys` mode

ImaginAI should still keep its own clean data store and mapping layer. The library is a communications library, not an app router.

## Gateway Responsibilities

`RotatorGateway` must:

- resolve `ModelConfig`
- load `ProviderConnection`
- load eligible `ProviderCredential` rows
- decrypt secrets only at call time
- build library classifier/scope arguments
- build provider override arguments for custom providers
- call `rotator_library`
- normalize streams/responses into ImaginAI events/results
- capture provider/usage metadata
- enforce no cross-user/global leakage before the library call

## Classifier Strategy

Use deterministic classifier strings generated by ImaginAI.

Recommended initial format:

```text
platform:connection:{provider_connection_id}
user:{user_id}:connection:{provider_connection_id}
```

Reason:

- credential pool and quota usually belong to provider connection
- model-level app stats can be tracked separately by ImaginAI
- works for global and user-owned models

## Provider Alias Strategy

The library still partly uses `provider/model` strings. ImaginAI should produce safe aliases.

For standard providers:

```text
openai/gpt-4.1
gemini/gemini-2.5-pro
openrouter/anthropic/claude-sonnet-4
```

For custom providers:

```text
custom_{stable_connection_slug}/model-name
```

If IDs contain unsafe characters, use a stable slug/hash.

## Per-Call Scoped Mode

Initial integration should use stateless per-call scoped routing:

1. Load model config.
2. Load provider connection.
3. Load/decrypt eligible credentials.
4. Build classifier/provider/API key args.
5. Call library with `private=True`.

Benefits:

- DB remains source of truth.
- No dependence on in-memory registered scopes.
- Correct after process restart.
- Simpler permissions and invalidation.

Later optimization:

- register scopes on startup/runtime
- invalidate/update registered scopes when DB changes

## Generation Flow

```text
GenerationService.generate(...)
  -> validate adventure ownership
  -> reconstruct adventure state
  -> resolve selected ModelConfig
  -> build prompt/messages
  -> call RotatorGateway.stream_completion(...)
  -> receive normalized stream events
  -> post-process visible output
  -> save variant/turn
  -> save PromptSnapshot and TokenUsage
```

The gateway should not know story concepts like cards/memory except as request metadata. The story engine passes already-built messages.

## Gateway Input DTO

Conceptual shape:

```text
RotatorCompletionRequest
- user_id
- model_config_id
- messages
- system, optional
- stream
- generation_params
  - temperature
  - top_p
  - provider_safety_max_tokens
  - thinking_enabled
  - thinking_budget
  - extra_params
- request_metadata
  - adventure_id
  - turn_id or variant_id
  - prompt_snapshot_id
```

## Gateway Output DTO

For non-streaming:

```text
RotatorCompletionResult
- text
- thinking, optional
- raw_response_metadata
- usage
  - prompt_tokens
  - completion_tokens
  - reasoning_tokens
  - total_tokens
  - cost_estimate
```

For streaming, normalize into events:

```text
thinking_delta
content_delta
usage_update
provider_metadata
done
error
```

## Security Checks Before Library Call

Gateway must assert:

- selected model config exists and is enabled
- current user can use selected model config
- global model uses only platform/global credentials
- user model uses only current user's credentials
- provider connection belongs to the same scope as the model config
- credentials belong to the selected provider connection
- no fallback credentials are added silently
- no raw secret enters logs, prompt snapshots, stream events, or API responses

## Model Discovery

Provider/model discovery flow:

```text
ProviderConnectionService
  -> validate ownership/permission
  -> load provider connection
  -> load eligible credential
  -> RotatorGateway.list_models(...)
  -> rotator_library.get_available_models(...)
```

Rules:

- user discovery uses user credential only
- global discovery uses platform credential only
- cache model lists in ImaginAI DB if useful
- allow manual model id entry when discovery fails

## Failure Handling

Gateway should normalize library/provider errors into app errors:

- `model_config_unavailable`
- `no_credentials`
- `provider_auth_failed`
- `provider_rate_limited`
- `quota_exhausted`
- `context_too_large`
- `provider_timeout`
- `provider_unavailable`
- `stream_interrupted`
- `unknown_provider_error`

User-facing errors must be safe. Admin/debug views can show deeper provider details without secrets.

## Allowed Library Refinement

Both ImaginAI and `rotator_library` are owned by the project owner. The library may be refined when the gateway has to fight it.

Do not push product concepts like scenarios, adventures, or ImaginAI users into the library. But library improvements are allowed for:

- typed scoped request objects
- normalized error contracts
- stream event normalization
- host-supplied credential IDs
- protocol dispatch
- structured model discovery results
- usage metadata completeness
- secret-safe diagnostics

Large library changes require a hard design document first. A separate library-focused agent should implement those changes.

## What Not To Do

- Do not call provider SDKs directly from story engine.
- Do not make `rotator_library` store ImaginAI model configs.
- Do not make scenario prompts part of model configs by default.
- Do not let user-owned models fall back to platform keys.
- Do not expose platform/global secrets to users.
- Do not rely only on library usage stats for ImaginAI debugging/billing/audit.
